# 国内版报批资料上传

本分支只用于浙江政务服务网 `recept.zjzwfw.gov.cn` 的“举办内地文艺表演团体、个人参加的营业性演出审批”。不得进入文化和旅游市场企业端，也不得套用涉外入出境、节目附件或提交页面规则。

## 上传前与网页守门

1. 演员必须全部为中国内地人员；混有外国、香港、澳门或台湾人员时改走涉外分支。
2. 按 [handoff.md](handoff.md) 生成/迁移唯一 JSON，并通过 `--stage materials` 后设置 `ready_for_portal_check: true`。空模板或结构检查通过不代表材料就绪。
3. 每次打开新浏览器会话、切换账号、草稿或事项时，先把 `ready_for_upload` 和 `runtime_qa` 重置，再核对当前 host、页面事项名称和目标演出/草稿。
4. 读取网页自动带出的“申报单位”，与 `application.applicant_entity.value` 的公司全称逐字一致后，设置当前会话主体门禁；简称相同不算通过，也不得覆盖网页自动字段。
5. 盘点页面已有演出计划、节目、演员和材料，和 JSON 对账；完全一致的跳过，缺项才补，冲突立即停止。所有当前会话门禁通过后才设 `ready_for_upload: true`，再按 handoff 的 `--stage upload` 验证当前上下文。

## 三个实体必须分开

- `applicant_entity`：统一使用主体配置的 `legal_name`；最终申请表、主体许可证、授权委托书和网页“申报单位”必须一致。旧主体材料是待解决冲突，不能靠改 JSON 或改已签章文件迁移。
- `venue_operator_entity`：场地运营/场地方，按实际场地材料核实，与申报主体分开记录。
- `venue_name`：实际演出场所名称，不是公司名；另存 `venue_address`。

主体许可证属于 `applicant_entity`；场地证明、场地方营业执照和消防材料应记录各自 `document_owner_entity`、`document_role`。归属不清或相互矛盾时不得上传。

## 上传前生成 JSON

1. 以最终申请表、许可证、授权委托书、节目单、演员名单和场地材料为主；文件名仅用于定位，不替代正文。
2. 所有可复制值记录 `semantic_type`、`value`、`source`、`target_field`；保留原文标点、空格、大小写和演员顺序。
3. 国内使用 `performance_plans[]` 表示一项或多项演出计划；每项同时保存日期、场次数、实际场所、场地运营方及附件。
4. 本地附件按 [handoff.md](handoff.md) 记录槽位、对象序号、角色、相对路径、大小、SHA-256、文件归属和上传次序；共享材料记录预期标题、所属主体和材料标识，不伪造本地路径或哈希。
5. 校验节目序号连续、演员人数一致、所有路径存在、格式符合槽位、主体和场地文件归属正确、跨文件名称与日期一致。冲突写入 `warnings`；有 warning 时材料和网页状态均须保持未就绪。
6. JSON 含证件号等敏感字段，仅保存在项目本地，不在聊天或日志中复述。

## 在线填表

### 基本信息

- 申报单位、法人代表、证件号码、企业地址、统一社会信用代码、证件类型等账号字段只核对，不覆盖。
- 录入/核对：演出区域、法定代表人电话、演出名称、主体许可证号、主要演出类型、主要演员（团体）、驻场演出、项目联络人、移动电话和电子邮箱。
- “主要演员（团体）”按最终演员名单顺序，多人用中文顿号连接。
- 类型按材料选择；训练案例的“流行乐”不能泛化到其他项目。
- 国内页面没有入境、出境日期，绝不使用涉外前后 10 天规则。

### 演出计划

按 `performance_plans[].sequence` 逐项新增：

1. 填开始日期、结束日期和场次数。
2. 填实际演出场所名称、类型、城市/区县和详细地址；不要把申报公司名称填成物理场所名称。
3. “场地证明”上传对应最终 PDF。
4. 页面因场所类型动态出现消防、营业执照等槽位时，严格按本计划 `upload_order` 上传。训练中“酒吧、饭店等非演出场所”槽位依次放消防开业证明和场地方营业执照，但只有当前页面槽位和 JSON 同时匹配才复用。
5. 确认后核对外层表格的日期、场次、场所、地址和附件；没有明确持久化信号时保持待核验，不能假定成功。

### 演出节目信息

1. 按 `programs[].sequence` 逐项新增，序号从 1 连续。
2. 页面“节目名称”使用 `display_name.value`，复制节目单整格原文。训练格式可能为 `《歌名（中文译名）》-演员名单`，因此不能只抽取歌名。
3. 节目类型使用 JSON 的页面值；页面无同名选项时同时保留 `source_value`、`value` 和 `mapping_reason`，不得静默替换。
4. 逐首“视听资料”上传一个与序号和标题匹配的视频；每首只上传一次。上传前以 `upload_id` 和页面现有文件名/大小去重。
5. 等待上传完成并确认列表新增后再处理下一首。总歌词不在逐首窗口上传，而在全局“上传材料”页上传一次。

### 参演人员信息

1. 按 `performers[].sequence` 填姓名、证件类型/号码、职务、性别、出生日期、长期有效或有效期，以及是否团体申请。
2. “有效身份证明”使用姓名完全匹配的最终 PDF；“演出协议或同意函件”使用对应签名/盖章材料。
3. 未成年人按 JSON 条件上传监护人同意函；成人不上传。以团体申请时才填写团体名称。
4. 保存后核对本行姓名、职务、日期、证件和同意函。重点防止证件号误入“职务”等粘贴错位。

## 上传材料

以 JSON 的 `material_uploads` 为唯一执行清单，按页面精确槽位、`upload_method` 和 `sequence` 上传。通用槽位通常包括申请表、节目单、演员名单、当前申报主体许可证、总歌词、经办人材料和授权委托书；页面实际槽位不同则停止核对，不能硬套训练案例。

训练中曾出现以下特殊映射：在“经办人身份证明”多文件槽位中依次放被委托人身份证明、委托人身份证明、歌词 PDF、翻译资质证明。它只能作为具体项目 JSON 中标记为 `recorded_case` 的清单，绝不是国内项目通则。

- 主体许可证使用共享材料时，再次核对材料所属公司全称等于 `applicant_entity`。
- 总歌词在“歌词或剧本文本”槽位全项目只上传一次。
- 同槽位多文件逐个等待文件名、大小和完成状态出现后再传下一个；慢速等待不得重复选择文件。

## 提交前核验与停止点

- 当前网站、事项、草稿和申报单位仍与本项目一致；当前会话门禁不是旧 JSON 遗留值。
- 申报主体、场地运营方和实际场所未混淆；主体许可证与场地方文件归属正确。
- 演出计划、节目和演员的页面数量与 JSON 完全一致，无重复、无缺项。
- 每首视频一次；总歌词只在材料页一次；所有槽位文件名、大小和状态完整。
- 若页面支持保存草稿，保存后重新只读核对关键列表/附件。判断“下一步”实际是否提交：仅进入信息确认且能持久化附件时可继续；若构成提交，已有明确提交授权且提交前核验完成时继续，无授权则停在已保存草稿页。
- 核验后按已有授权继续；无最终提交授权时停在承诺/提交前。用户已明确授权提交的，不再重复请求。
